# openEO history export format

This document describes the **input format** that
`services/api/scripts/import_openeo_history.py` expects so that an openEO
Sentinel-2 (and optional EFAS) export can replace the synthetic baseline in
`services/api/app/data/aoi_history.json` without touching any UI code.

The current baseline (96 months, Jan 2018 – Dec 2025) is generated by
`services/api/scripts/generate_baked_history.py` with seasonality calibrated
to match the openEO Sentinel-2 trend figure. It is meant to be **replaced**
once the real export lands.

## Channels consumed by the app

The mobile app's `_HistoryChart` widget (in `simulate_tab.dart`) currently
reads two columns per monthly observation:

| Field                   | Type    | Range                  | Source                                           |
| ----------------------- | ------- | ---------------------- | ------------------------------------------------ |
| `ndsi_snow_fraction`    | float   | `[0.0, 1.0]`           | Sentinel-2 NDSI ≥ 0.4 fraction over AOI bbox     |
| `efas_anomaly_percent`  | float   | `[-50.0, +50.0]`       | CDS Lisflood-EFAS seasonal discharge anomaly (%) |

Additional indices (`ndvi`, `ndwi`, `snow_fraction`, `water_fraction`) from
the openEO pipeline are tolerated by the importer and stored for future use,
but the chart only renders the two above. We can wire the rest in once the
export is available; see "Forward extensions" below.

## Accepted input formats

The importer auto-detects the file extension. Pick whichever your openEO
notebook can produce most easily.

### 1. CSV (recommended — easiest to ship out of a Jupyter cell)

One row per (AOI, month). The header row must include `aoi` and `month`.

```csv
aoi,month,ndsi_snow_fraction,efas_anomaly_percent,ndvi,ndwi
oetztal-alps,2018-01,0.78,-3.4,-0.04,0.05
oetztal-alps,2018-02,0.82,-1.2,-0.05,0.04
inn-valley,2018-01,0.71,-4.1,-0.03,0.04
...
```

Required columns:

* `aoi` — slug used in the JSON cache. Must be one of `oetztal-alps`,
  `inn-valley`, or a new slug (in which case add it to the importer's
  `ALIASES` table or pass `--alias` flags).
* `month` — `YYYY-MM` string.
* `ndsi_snow_fraction` **or** `snow_fraction` — at least one snow channel.
* `efas_anomaly_percent` — optional. If absent, the importer fills with `0.0`
  and warns; the EFAS series will still render but flat.

Optional columns are passed through verbatim and stored at the AOI level.

### 2. JSON

Same shape as the existing `aoi_history.json` file. Useful when the openEO
notebook already produces a structured dict.

```json
{
  "histories": {
    "oetztal-alps": {
      "label": "Oetztal Alps",
      "aliases": ["oetztal", "oetztal alps aoi"],
      "source": "openEO platform Sentinel-2 NDSI + CDS EFAS",
      "provenance": "...",
      "points": [
        { "month": "2018-01", "ndsi_snow_fraction": 0.78, "efas_anomaly_percent": -3.4 },
        ...
      ]
    }
  }
}
```

### 3. Pandas DataFrame in a notebook (no separate file)

If the colleague prefers, a one-liner in their notebook produces the CSV the
importer expects:

```python
df.to_csv("openeo_history.csv", index=False)
# then on the API side:
# python scripts/import_openeo_history.py openeo_history.csv
```

The DataFrame must have the columns described under "CSV" above.

## AOI naming and aliases

The frontend looks up history by **AOI label** (e.g. `"Oetztal Alps AOI"` or
`"Inn Valley AOI"` — see `RiskTimeline.waterBodyName`). The backend matches
these labels case-insensitively against `label` and any `aliases` listed in
the JSON entry.

If your colleague's export uses a different identifier (e.g.
`oetztal_2024_v3`), pass the mapping at import time:

```bash
python scripts/import_openeo_history.py \
  --alias "oetztal_2024_v3=oetztal-alps" \
  openeo_history.csv
```

The importer rewrites identifiers to the canonical slug before writing.

## Recommended AOI bounding boxes

To keep the openEO request consistent with the API's AOI presets, use the
same bounding boxes that `map_screen.dart` ships (WGS84):

* **Inn Valley AOI**: `47.18, 11.20, 47.40, 11.85` (south, west, north, east)
* **Oetztal Alps AOI**: `46.84, 10.65, 47.30, 11.10`

## What the chart will do with the data

* Plot the observed NDSI and EFAS series across the full window.
* Fit an ordinary least-squares regression on each series.
* Extrapolate the regression **24 months past** the last observation as a
  dashed projection line, and feed the slope into the SimulateTab caption
  ("NDSI -0.027/yr · EFAS +1.4 pp/yr").
* Tooltip-distinguish observed vs projected points (italicised, "(proj.)").

## Forward extensions (not blocking the merge)

When the export includes them, we can add:

1. **NDVI / NDWI / SnowFrac / WaterFrac** — wire each as a toggle in the
   chart card so judges can flip between channels (matches the colleague's
   top-panel figure).
2. **Water-mask raster (NDWI > 0.1)** — pre-render to a transparent PNG and
   overlay on `map_screen.dart` as a `TileLayer.overlay` for the Ötztal AOI.
3. **Per-pixel trend maps** — same overlay pattern; expose as an optional
   layer toggle alongside the SAR flood mask.

None of these are required to take the openEO data live; they're the
natural follow-ups once the time series is in place.
